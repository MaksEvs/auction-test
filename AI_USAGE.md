# Использование AI

AI использовался как инструмент ускорения разработки, ревью и проверки гипотез.
Ответственность за архитектуру, соответствие OpenAPI, принятые решения и итоговое
состояние проекта оставалась на мне.

## Что делалось с помощью AI

Проект достаточно объёмный для тестового задания, поэтому агент помогал быстрее
реализовать повторяющиеся и хорошо формализуемые части:

- API-функции и TanStack Query hooks;
- MSW handlers, mutable mock store и тестовые данные;
- DTO-типы и мапперы list/detail responses;
- формы и Zod-схемы;
- UI-секции деталей и истории ставок;
- вспомогательные функции для форматирования, расчёта доступной цены и проверки
  ставки;
- unit- и component-тесты;
- рефакторинг импортов, naming и FSD-зависимостей.

Основная часть кода генерировалась агентом небольшими patch-итерациями. Каждый
patch я просматривал построчно до применения, проверял его место в архитектуре и
запускал lint, tests или build после значимых изменений. Если мне было
бы быстрее и надёжнее внести небольшое изменение самостоятельно — например,
исправить локальный баг или поменять поведение компонента — я бы не использовал AI
ради самого факта его использования.

Zod и Zustand до проекта не входили в мой основной рабочий набор. Первичное
применение и небольшие примеры я делал самостоятельно, чтобы понять модель работы
библиотек. После этого агент помог масштабировать выбранные подходы на весь проект.

## Какие решения я принял самостоятельно

- Определил способ совместного применения обязательного стека, выбрал MUI,
  Zustand и структуру Feature-Sliced Design.
- Определил границы `app`, `pages`, `features`, `entities` и `shared`, а также
  направления зависимостей между ними.
- Оставил `fetch` вместо дополнительного HTTP-клиента.
- Выбрал простую понятную пагинацию, вместо пагинации через бесконечный скролл
- Использовал Zustand только для глобального notification UI-state, не перенося в
  него server state из TanStack Query.
- Разделил client validation формы и authoritative validation в MSW handler.
- Решил не расширять list DTO неописанным полем `step`: схема API передана как
  источник правды, а в `AuctionListItemTradingPrice` этого поля нет.
- Для недоступной ставки сделал action «Смотреть ставки», соответствующий ТЗ.
- Сохранил фильтры и страницу списка при переходах в детали, историю и форму.
- Добавил отдельное отображение 404 как для неизвестного route, так и для
  неизвестного UUID аукциона.

## Какие предложения AI были отклонены

- **Добавить Axios.** Я оставил native `fetch`: API небольшой, interceptors,
  cancellation helpers и остальные возможности Axios здесь не дают достаточной
  пользы для новой зависимости.
- **Добавить `step` в list response вручную.** Это закрыло бы UI-чеклист, но
  нарушило бы переданный OpenAPI-контракт.
- **Загружать details для каждой карточки ради `step`.** Решение создало бы N+1
  requests и усложнило состояния списка.
- **Реализовать отдельные MSW-сценарии для всех `401` и `503` уже сейчас.** Для
  текущего объёма оставлена общая обработка ошибок; расширенную демонстрацию я
  вынес в возможные улучшения.
- Состояние для скрытия фильтров

## Что проверялось особенно внимательно

- соответствие request/response DTO переданной OpenAPI-схеме;
- enum-значения, nullable-поля и различия list/detail contracts;
- направление FSD-зависимостей и отсутствие относительных импортов;
- URL parsing, fallback-значения и преобразование фильтров в API request;
- расчёт следующей доступной цены для `Up` и `Down`, min/max boundaries и
  приоритет server guards;
- изменение MSW store после mutation: цена, available price, место, статус
  пользователя и список ставок;
- invalidation list/detail/bets queries;
- обработка `422 ValidationFailed` и отображение server error у поля;
- hidden contacts, hidden history, empty history и nullable data;
- поведение прямых ссылок и API 404;
- каждый сгенерированный patch, после чего выполнялись tests, lint и build.

## Оставшиеся риски

- Ручная проверка в большом наборе реальных браузеров и размеров экрана ограничена;
  responsive layout построен на MUI breakpoints, но возможны локальные визуальные
  проблемы с длинными значениями.
- Mock backend покрывает основной контракт и 422, но не содержит отдельных
  управляемых demo-сценариев для каждого `401`, `503` и network failure.
- OpenAPI имеет внутренние расхождения в nullable/required и enum declarations;
  реализация следует ожидаемой семантике, но реальный backend может уточнить эти
  поля иначе.
- In-memory MSW store сбрасывается после перезагрузки вкладки и не моделирует
  конкурентные ставки нескольких пользователей.
- Production bundle пока собирается одним крупным chunk.
- Автотесты хорошо покрывают чистую логику и форму ставки, но не заменяют полный
  browser E2E flow списка, фильтров, навигации и mutation.

## Что бы я улучшил при наличии ещё одного дня

1. Добавил полнотекстовый поиск и улучшил UX сложной панели фильтров.
2. Реализовал отдельные состояния и MSW fixtures для `401`, `503`, timeout и
   network errors, а также retry action.
3. Провёл дополнительный UI-polish: собственную визуальную систему поверх MUI,
   более выразительную иерархию, иконки, состояния hover/focus и mobile UX.
4. Сделал всю карточку аукциона кликабельной для перехода в детали, сохранив
   отдельный primary action для ставки или истории.
5. Добавил route-level lazy loading и code splitting.
6. Провёл расширенную accessibility-проверку: keyboard-only flow, screen reader
   labels, focus order и contrast.
7. Реализовал бы полноценный CI CD, подключив пайплайны с тестами и сборкой билда в git,
   что бы в будущем чужой код ничего не сломал
8. Переделал бы в микрофронт, что бы удобно подключать к другим проектам
